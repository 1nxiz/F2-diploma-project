## Context

Ключовий інваріант системи: для одного робочого місця множина підтверджених бронювань не містить інтервалів, що перетинаються ([SRS-FUN-11](../srs.md#srs-fun-11)). SRS вимагає:

- 100 одночасних запитів на одне місце → рівно 1 успіх і 0 перетинів у БД ([SRS-NFR-CONS-01](../srs.md#srs-nfr-cons-01));
- p95 Latency `POST /bookings` ≤ 300 мс при 50 RPS ([SRS-NFR-PERF-02](../srs.md#srs-nfr-perf-02));
- запуск 2 і більше stateless-реплік API ([SRS-NFR-SCAL-01](../srs.md#srs-nfr-scal-01)), тобто блокування в пам'яті процесу неприйнятне;
- відсутність подвійних бронювань за недоступності Redis ([SRS-NFR-REL-02](../srs.md#srs-nfr-rel-02));
- вікно 120 с між вибором місця та підтвердженням ([SRS-FUN-10](../srs.md#srs-fun-10)).

Обмеження: розгортання на одному хості (Docker Compose), одна інстанція PostgreSQL, одна інстанція Redis.

## Alternatives

| # | Альтернатива | Гарантія відсутності перетинів | Обмеження |
| --- | --- | --- | --- |
| A | Перевірка в коді + `SELECT … FOR UPDATE` рядка `workspaces` | Так, якщо всі шляхи запису беруть блокування | Блокування утримується протягом усієї транзакції; гарантія залежить від дисципліни коду, а не від схеми; не дає вікна 120 с |
| B | Рівень ізоляції `SERIALIZABLE` (SSI) | Так | Відкати з SQLSTATE 40001 вимагають циклу повторів; частка відкатів зростає пропорційно конкуренції за одне місце (100 VU → до 99 відкатів з повторами), що збільшує p95 |
| C | Лише Redis-блокування (`SET NX PX` або Redlock) | Ні | Пауза процесу (GC, мережа) довша за TTL дозволяє двом клієнтам вважати себе власниками блокування; без fencing token гарантія відсутня; за відмови Redis бронювання неможливе |
| D | Лише `EXCLUDE USING gist` у PostgreSQL | Так, декларативно в СУБД | Немає вікна 120 с на підтвердження; кожна конфліктна спроба доходить до БД і виконує вставку з відкатом |
| **E** | **`EXCLUDE USING gist` + Redis hold (`SET NX PX`)** | **Так (гарантія — PostgreSQL)** | Додаткова залежність від Redis; дві підсистеми в критичному шляху |

## Decision

Обрано альтернативу **E**.

1. **Гарантія коректності — PostgreSQL.** Таблиця `bookings` має колонку `period tstzrange` та обмеження:

   ```sql
   CREATE EXTENSION IF NOT EXISTS btree_gist;
   ALTER TABLE bookings ADD CONSTRAINT bookings_no_overlap
     EXCLUDE USING gist (workspace_id WITH =, period WITH &&)
     WHERE (status IN ('confirmed', 'completed'));
   ```

   Порушення (SQLSTATE `23P01`) транслюється адаптером SQLAlchemy у доменний виняток `BookingConflict` і далі у відповідь 409. Обмеження діє незалежно від коду застосунку, Redis і кількості реплік.
2. **Зниження конкуренції та вікно підтвердження — Redis.** `SET hold:{workspace_id}:{start} {token} NX PX 120000` атомарно резервує місце на 120 с. Друга спроба на той самий початок інтервалу (типовий випадок конкуренції) отримує 409 без звернення до PostgreSQL; часткові перетини з іншим початком відсікає обмеження з п. 1. Зняття блокування виконується Lua-скриптом з перевіркою токена власника.
3. **Деградація.** За недоступності Redis `POST /holds` повертає 503, а `POST /bookings` приймається без hold; коректність забезпечує п. 1 ([SRS-NFR-REL-02](../srs.md#srs-nfr-rel-02)).

Відмова від A–D обґрунтована метриками: A і D не забезпечують вікна підтвердження; B збільшує p95 через повтори за високої конкуренції за одне місце; C не має гарантії коректності за паузи процесу, довшої за TTL.

## Consequences

**Позитивні:**

- Інваріант «немає перетинів» перевіряється СУБД; тест [SRS-NFR-CONS-01](../srs.md#srs-nfr-cons-01) і SQL-запит на перетини мають детермінований результат.
- Гранулярність блокування — одне місце (а не локація, як у Seatsurfing), тому запити до різних місць не серіалізуються.
- Конфліктні спроби відсікаються в Redis до транзакції PostgreSQL, що зменшує навантаження на пул з'єднань БД.
- Реплікація API не потребує змін: стан блокувань зберігається в Redis і PostgreSQL.

**Негативні та ризики:**

- **Дві підсистеми в критичному шляху.** Redis — єдина точка відмови для hold (кластер не передбачено); пом'якшено режимом деградації.
- **Залежність від розширення `btree_gist`** і специфічних для PostgreSQL типів (`tstzrange`): перенесення на іншу СУБД потребує переписування обмеження (vendor lock-in на рівні СУБД). Тестові БД (SQLite) не підтримують `EXCLUDE`, тому інтеграційні тести потребують реального PostgreSQL у testcontainers, що збільшує тривалість CI орієнтовно на 30–60 с на запуск.
- **Міграції:** додавання обмеження до заповненої таблиці потребує попереднього пошуку та усунення наявних перетинів; міграцію Alembic слід виконувати з `lock_timeout`.
- **Hold не є гарантією.** Розробники не повинні покладатися на hold як на доказ доступності; це правило зафіксовано в описі компонента `HoldStore`.
- **FinOps.** У разі переходу з локального розгортання до хмари з'являється окрема вартість керованого Redis (наприклад, найменший вузол ElastiCache / Memorystore); для поточного обсягу витрати відсутні, оскільки Redis працює в Docker Compose.
- **Тестування:** потрібні сценарії fault injection (зупинка Redis) і перевірка трансляції `23P01` → 409.
