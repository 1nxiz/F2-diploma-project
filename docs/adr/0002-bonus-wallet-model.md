# ADR-002: Модель бонусного рахунку — баланс з `CHECK` + журнал транзакцій з `UNIQUE`

## Context

Бонусна програма вимагає: нарахування 5 балів/год після завершення бронювання, шкалу 0–100 без накопичення понад 100, обмін 100 балів на безкоштовну годину з обнуленням шкали та денний ліміт 5 год у межах коворкінгу. Нарахування виконує Scheduler Worker, який може бути запущений повторно після збою; використання бонусу ініціює користувач, у тому числі повторними натисканнями. SRS вимагає рівно одного нарахування на бронювання ([SRS-NFR-CONS-03](../srs.md#srs-nfr-cons-03)) і рівно одного успіху з 20 паралельних запитів на безкоштовну годину ([SRS-NFR-CONS-04](../srs.md#srs-nfr-cons-04)).

## Alternatives

| # | Альтернатива | Обмеження |
| --- | --- | --- |
| A | Лише колонка `balance` в `users` | Немає захисту від повторного нарахування після рестарту Worker; немає аудиту; один рахунок на всі коворкінги суперечить [SRS-BR-01](../srs.md#srs-br-01) |
| B | Лише журнал транзакцій, баланс = `SUM(points)` | Перевірка «баланс = 100» і ліміту потребує агрегації журналу в кожній транзакції; обмеження 0–100 неможливо задати декларативним `CHECK` |
| C | Лічильник у Redis (`INCRBY`) | Redis не є джерелом істини; втрата даних за рестарту без AOF; відсутня транзакційність разом з бронюванням |
| **D** | **Таблиця `bonus_wallets` (`balance` з `CHECK 0..100`) + таблиця `bonus_transactions` з `UNIQUE (booking_id, type)`, оновлення в одній транзакції** | Дві таблиці потрібно змінювати узгоджено |

## Decision

Обрано альтернативу **D**.

- `bonus_wallets (user_id, coworking_id, balance, updated_at)`, PK (`user_id`, `coworking_id`), `CHECK (balance BETWEEN 0 AND 100)`.
- `bonus_transactions (id, user_id, coworking_id, booking_id, type, points, created_at)`, `UNIQUE (booking_id, type)`, `type ∈ {accrual, redemption, restore}`.
- **Нарахування (Worker):** в одній транзакції `UPDATE bookings SET status = 'completed' … FOR UPDATE SKIP LOCKED` → `INSERT INTO bonus_transactions … ON CONFLICT DO NOTHING` → якщо вставка відбулася, `UPDATE bonus_wallets SET balance = LEAST(100, balance + :points)`.
- **Денний ліміт (API):** створення бронювання блокує рядок рахунку `SELECT … FROM bonus_wallets WHERE user_id = :u AND coworking_id = :c FOR UPDATE` (рядок створюється через `INSERT … ON CONFLICT DO NOTHING`), після чого сумує тривалості за добу. Блокування серіалізує лише запити цього користувача в цьому коворкінгу.
- **Безкоштовна година (API):** `UPDATE bonus_wallets SET balance = 0 WHERE … AND balance = 100 RETURNING` + вставка бонусного бронювання (обмеження ADR-001) + запис `redemption` — в одній транзакції; 0 оновлених рядків → 409.

## Consequences

**Позитивні:**

- Повторний запуск Worker не дає повторного нарахування (`UNIQUE` + `ON CONFLICT DO NOTHING`).
- Інваріант 0–100 гарантує СУБД (`CHECK`), а не код.
- Умовне оновлення `WHERE balance = 100` робить використання бонусу атомарним без окремого блокування.
- Журнал дає повний аудит змін балансу.

**Негативні та ризики:**

- Баланс денормалізований: потрібен періодичний тест звірки `balance = LEAST(...)` з журналом; розбіжність можлива лише за ручного втручання в БД.
- `SELECT … FOR UPDATE` рядка рахунку додає одне блокування рядка в транзакцію створення бронювання (вплив на p95 — у межах [SRS-NFR-PERF-02](../srs.md#srs-nfr-perf-02), перевіряється k6).
- Нарахування за рахунок, що вже має 100 балів, повертає 0 балів; запис `accrual` з `points = 0` фіксується для аудиту, щоб пояснити користувачу, чому бали не додані.
- Межі доби залежать від часового поясу коворкінгу; зміна `timezone` адміністратором змінює межі доби для майбутніх бронювань — зміну заборонено за наявності майбутніх бронювань.
