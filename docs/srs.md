## 1. Вступ

### 1.1 Призначення

Документ встановлює обов'язкові вимоги до CoWork Booking System і є контрактом між постановкою задачі (Розділ 1) та архітектурою (Розділ 2). Кожна вимога має унікальний ідентифікатор, на який посилаються діаграми C4, ADR і тести.

### 1.2 Конвенції

- «повинна» — обов'язкова вимога; невиконання означає невідповідність системи SRS.
- Пріоритет: **M** (Must) — обов'язково для захисту; **S** (Should) — реалізується за наявності часу в межах календарного плану.
- Ідентифікатори: `SRS-FUN-NN` — функціональні вимоги, `SRS-BR-NN` — бізнес-правила, `SRS-NFR-<КАТ>-NN` — нефункціональні вимоги.
- Час зберігається в UTC; межі календарної доби визначаються часовим поясом коворкінгу (IANA, наприклад `Europe/Kyiv`).

### 1.3 Обсяг (Scope)

**У межах системи:** реєстрація та автентифікація, каталог коворкінгів, зон і робочих місць, пошук доступності, тимчасове блокування (hold), бронювання та скасування, денний ліміт 5 год, бонусна програма лояльності, історія бронювань, адміністрування каталогу, email-сповіщення, метрики та журнали.

**Поза межами системи:** онлайн-оплата, інтеграція з календарями (CalDAV, Microsoft 365), SSO через зовнішній IdP, мобільний застосунок, аналітика зайнятості, фізичний контроль доступу.

## 2. System Context (Контекст системи)

### 2.1 Межі та зовнішні взаємодії

Система розгортається як набір контейнерів Docker Compose і взаємодіє з такими зовнішніми сутностями:

| Зовнішня сутність | Тип | Інтерфейс | Призначення |
| --- | --- | --- | --- |
| Резидент | Person | HTTPS, REST JSON через браузер | Пошук, бронювання, бонусний рахунок |
| Адміністратор коворкінгу | Person | HTTPS, REST JSON через браузер | Керування каталогом і бронюваннями |
| Email Service (SMTP relay) | External system | SMTP + STARTTLS, порт 587 | Доставка сповіщень |

### 2.2 Класи користувачів

| Роль | Права |
| --- | --- |
| Гість | Реєстрація, автентифікація |
| Резидент (`user`) | Пошук, hold, власні бронювання, власний бонусний рахунок |
| Адміністратор (`admin`) | Усі права резидента + каталог, усі бронювання |
| Scheduler Worker (системний актор) | Завершення бронювань, нарахування балів, надсилання листів |

### 2.3 Обмеження проєктування

- Стек: Python 3.12, FastAPI, SQLAlchemy 2.0, PostgreSQL 17 (розширення `btree_gist`), Redis 7, React + TypeScript, Nginx, Docker Compose, GitHub Actions.
- Розгортання: один хост (4 vCPU, 8 GB RAM); реплікація БД і кластер Redis не передбачені.
- Архітектурний стиль: модульний моноліт (API Application) + окремий процес Scheduler Worker на спільній кодовій базі.

### 2.4 Припущення

- Тривалість бронювання кратна 1 год; початок кратний 30 хв.
- Один користувач може бути резидентом кількох коворкінгових компаній; ліміти та бонусний рахунок ведуться окремо для кожної.

### 3.5 Бізнес-правила бонусної програми

| ID | Правило |
| --- | --- |
| <a id="srs-br-01"></a>SRS-BR-01 | Бонусний рахунок ідентифікується парою (`user_id`, `coworking_id`); рахунки різних коворкінгів незалежні. |
| <a id="srs-br-02"></a>SRS-BR-02 | Денний ліміт: сума тривалостей оплачуваних (`kind = regular`) бронювань зі статусами `confirmed` і `completed`, що починаються в межах однієї календарної доби коворкінгу, — не більше 5 год. |
| <a id="srs-br-03"></a>SRS-BR-03 | Нарахування: 5 балів × кількість годин завершеного оплачуваного бронювання (1 год → 5, 2 год → 10, 5 год → 25). |
| <a id="srs-br-04"></a>SRS-BR-04 | Баланс обмежений діапазоном 0–100; нараховується `min(5 × години, 100 − баланс)`, надлишок не зберігається. |
| <a id="srs-br-05"></a>SRS-BR-05 | Скасовані (`cancelled`) і бонусні (`kind = bonus`) бронювання бали не нараховують. |
| <a id="srs-br-06"></a>SRS-BR-06 | Безкоштовна година доступна лише за балансу 100 і лише як продовження власного підтвердженого оплачуваного бронювання, що ще не завершилося. |
| <a id="srs-br-07"></a>SRS-BR-07 | Бонусне бронювання не враховується в денний ліміт SRS-BR-02. |
| <a id="srs-br-08"></a>SRS-BR-08 | Якщо інтервал продовження зайнятий, активація відхиляється з кодом 409, баланс не змінюється. |
| <a id="srs-br-09"></a>SRS-BR-09 | Кожна зміна балансу фіксується записом журналу (`accrual`, `redemption`, `restore`); для пари (`booking_id`, `type`) допускається лише один запис. |

## 6. Glossary (Глосарій)

| Термін | Визначення |
| --- | --- |
| Hold | Тимчасове блокування робочого місця на інтервал у Redis (`SET key token NX PX 120000`), що не є гарантією коректності, а зменшує кількість конфліктів |
| `EXCLUDE USING gist` | Обмеження PostgreSQL, яке забороняє два рядки з однаковим `workspace_id` і перетином діапазонів `period` (`tstzrange`, оператор `&&`) |
| Бонусний рахунок (BonusWallet) | Запис (`user_id`, `coworking_id`, `balance`) із балансом 0–100 балів |
| Безкоштовна година | Бонусне бронювання на 1 год одразу після закінчення оплачуваного бронювання, отримане в обмін на 100 балів |
| p95 Latency | Значення часу відповіді, яке не перевищують 95 % запитів у вибірці |
| RPS | Кількість HTTP-запитів за секунду, що надходять до системи |
| JWT | JSON Web Token (RFC 7519): підписаний токен з ідентифікатором користувача (`sub`), роллю та строком дії (`exp`) |
| Idempotency-Key | Заголовок запиту з унікальним ключем, за яким сервер повертає результат першої обробки замість повторного виконання операції |
| Race condition | Стан гонитви: результат залежить від порядку виконання паралельних операцій над спільним станом |
| RBAC | Role-Based Access Control — керування доступом на основі ролей (`user`, `admin`) |
