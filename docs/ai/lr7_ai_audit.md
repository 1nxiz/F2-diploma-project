# Протокол роботи з ШІ (AI Disclosure), ЛР №7

Документ фіксує використання генеративного ШІ під час виконання ЛР №7 «Проєктування архітектури, API та безпеки». Для кожного завдання наведено: що згенеровано (чернетка), який аудит виконано, які зауваження прийнято або відхилено та чому.

| Параметр | Значення |
| --- | --- |
| Інструмент | Claude (Anthropic), агентний режим з доступом до репозиторію |
| Роль ШІ під час генерації | Співавтор чернеток: текст, діаграми Mermaid, файл StarUML, скрипти перевірки |
| Роль ШІ під час аудиту | Рецензент у ролі Senior Software Architect / AppSec Engineer з окремою інструкцією «знайди розбіжності, не хвали» |
| Відповідальність | Рішення про прийняття змін і зміст пояснювальної записки — автор роботи |
| Обмеження | Аудит виконано тією самою моделлю, що й генерацію, тому він не замінює рецензію викладача; автоматичні перевірки (markdownlint, валідатор OpenAPI, скрипти) усувають частину цього обмеження |

Шкала критичності зауважень: **H** — порушує вимогу або контракт; **M** — неоднозначність, що вплине на реалізацію; **L** — оформлення.

## Завдання 1. Архітектурний стиль і патерни (підрозділ 2.1)

**Промпт аудиту:** «Ти — Senior Software Architect. Перевір обґрунтування стилю модульного моноліту для системи з вимогами SRS-NFR-CONS-01…04, SRS-NFR-SCAL-01. Чи кожен патерн прив'язаний до вимоги? Чи не суперечить вибір стилю наявним ADR? Відповідай списком зауважень з критичністю».

| № | Зауваження аудитора | Крит. | Рішення |
| --- | --- | :---: | --- |
| 1.1 | Обґрунтування стилю спирається на «простоту», без зв'язку з вимогами консистентності | H | Прийнято: додано три групи чинників з посиланнями на SRS-NFR-CONS-01…04, SRS-FUN-22, SRS-FUN-32 |
| 1.2 | Немає порівняння з альтернативними стилями | M | Прийнято: додано таблицю з чотирма стилями та причинами відхилення |
| 1.3 | Патерни перелічено без місця застосування | M | Прийнято: таблиця «патерн — де — яку проблему розв'язує — вимога» |
| 1.4 | Правило залежностей Clean Architecture не перевіряється автоматично | M | Прийнято: зазначено контракт `import-linter` у CI |
| 1.5 | Рекомендовано виділити модуль асистента в окремий мікросервіс через зовнішню залежність від LLM | M | Відхилено: підтвердження пропозиції створює бронювання в одній транзакції з перевіркою ліміту (SRS-FUN-32); межу модуля описано так, щоб виділення було можливим пізніше |
| 1.6 | Рекомендовано Outbox для email-сповіщень | L | Відкладено: дублювання листа не критичне, а поле `cap_notified_at` запобігає повторному надсиланню; рішення можна переглянути на етапі реалізації |

## Завдання 2. Діаграма та специфікації варіантів використання (підрозділ 2.6)

**Промпт аудиту:** «Перевір діаграму варіантів використання на відповідність UML 2.5: межа системи, первинні актори ліворуч, вторинні праворуч, напрямок стрілок «include»/«extend», узагальнення. Перевір специфікації UC: чи кожен крок Happy Path має конкретний виклик API або SQL, чи кожен AF має точку початку й повернення, чи EF описують відкат».

| № | Зауваження аудитора | Крит. | Рішення |
| --- | --- | :---: | --- |
| 2.1 | Лінія «extend» UC-06 → UC-05 перетинала еліпс UC-15; лінія асоціації Резидента перетинала UC-04 | L | Прийнято: змінено розміщення (UC-15 під UC-05, UC-06 у правій колонці), асоціації спрямовано до лівого краю еліпсів |
| 2.2 | Стрілка «extend» має йти від розширення до базового варіанта | H | Перевірено: напрямок правильний (UC-09 → UC-04, UC-15 → UC-05, UC-06 → UC-05, UC-17 → UC-11) |
| 2.3 | Таймер (Scheduler) — не людина; чи коректно позначати його актором | M | Відхилено: UML допускає зовнішній ініціатор за часом як актора; він ініціює UC-11 і розміщений ліворуч як первинний |
| 2.4 | У UC-05 не визначено, як рахується денний ліміт для групи місць | H | Прийнято: ліміт рахується як сума тривалостей усіх бронювань групи (крок 5, EF-05.2) |
| 2.5 | EF-05.5 повертав `expires_at = null`, але в OpenAPI поле обов'язкове і має формат `date-time` | H | Прийнято: сценарій змінено — пропозиція створюється без hold, коректність забезпечує `EXCLUDE` |
| 2.6 | UC-09 не перевіряє, чи година продовження вкладається в робочі години | M | Прийнято: доповнено SRS-BR-06, додано EF-09.4 |
| 2.7 | Повторна безкоштовна година для того самого батьківського бронювання не заблокована на рівні БД | M | Прийнято: частковий унікальний індекс `bookings_one_bonus_per_parent` |
| 2.8 | Рекомендовано «include» UC-04 → UC-03 (пошук перед бронюванням) | L | Відхилено: пошук не обов'язковий — бронювання можливе за відомим місцем (наприклад, з історії) |

## Завдання 3. Матриця маршрутів API та потоки даних (підрозділ 2.5)

**Промпт аудиту:** «Порівняй матрицю маршрутів з `openapi.yaml`: методи, URI, тіла, доступ. Перевір наскрізні правила: Max Body Size, CORS, пагінація, IDOR. Знайди маршрути без авторизації та з можливістю BOLA».

| № | Зауваження аудитора | Крит. | Рішення |
| --- | --- | :---: | --- |
| 3.1 | SRS-NFR-PERF-01 посилається на `GET /api/v1/workspaces/availability`, якого немає в контракті | H | Прийнято: SRS і розділ 1 приведено до `GET /api/v1/coworkings/{coworking_id}/availability` |
| 3.2 | Ручна звірка матриці з OpenAPI ненадійна | M | Прийнято: скрипт `scripts/check_api_matrix.py` у CI (24 / 24) |
| 3.3 | Для `DELETE /holds/{hold_token}` не описано перевірку власника | H | Прийнято: значення ключа Redis містить `user_id`, Lua-скрипт порівнює його перед видаленням (2.4.2) |
| 3.4 | Для чужого ресурсу повертати 403 | M | Відхилено: повертається 404, щоб не розкривати існування ресурсу (рекомендація OWASP API1) |
| 3.5 | Не визначено поведінку за повтору `Idempotency-Key` з іншим тілом | M | Прийнято: 422 (2.5.3) |
| 3.6 | `/health/*` доступні без автентифікації | L | Прийнято з уточненням: маршрути не проксіюються Nginx назовні |
