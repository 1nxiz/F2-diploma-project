# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ТЕХНІЧНЕ ЗАВДАННЯ

## 1.2 Аналіз існуючих аналогів

Для аналізу обрано три програмні системи, що розв'язують задачу керування робочими місцями та їх бронювання: комерційні SaaS-платформи Nexudus і OfficeRnD Flex та open-source систему Seatsurfing. Аналоги розглянуто як інженерні системи за чотирма аспектами: архітектурний патерн, протоколи передачі даних, стек даних і механізми консистентності, технічні обмеження (Technical Bottlenecks). Характеристики комерційних систем встановлено за офіційною документацією API; характеристики Seatsurfing — за вихідним кодом репозиторію (commit `190ad07` від 27.10.2026). Характеристики, які вендор публічно не розкриває, позначено відповідно і в порівнянні не використовуються.

### 1.2.1 Nexudus

**Архітектурний патерн.** Закрита мультиорендна (multi-tenant) SaaS-платформа. Внутрішня декомпозиція системи публічно не розкривається. Зовнішній контракт — централізований REST API (`https://spaces.nexudus.com/api`) та окремий Public API для клієнтських застосунків. Горизонтальне масштабування контролюється вендором.

**Протоколи передачі даних.** REST over HTTPS із форматом JSON; методи GET, POST, PUT, DELETE. Приймаються з'єднання TLS 1.2 і вище. Автентифікація — Bearer token або HTTP Basic Auth. Для інтеграцій передбачено webhooks.

**Стек даних і консистентність.** Тип СУБД не розкривається; доменна модель реляційна (опубліковано ERD сутностей Coworker, Booking, Checkin). Механізми контролю паралельних змін (ETag, версія запису) в огляді API не задокументовано.

**Technical Bottlenecks:**

- метод PATCH не підтримується, тому оновлення виконується через повну заміну запису (PUT) за схемою read-modify-write; за паралельного редагування без оптимістичного блокування виникає ризик втрати оновлення (lost update);
- підтримка HTTP Basic Auth передбачає передавання облікових даних у кожному запиті;
- залежність від вендора (vendor lock-in): схема даних, розгортання та інфраструктурний SLA перебувають поза контролем інтегратора.

### 1.2.2 OfficeRnD Flex

**Архітектурний патерн.** Мультиорендна SaaS-платформа. API v2 побудовано на NestJS (Node.js, TypeScript) із DTO-схемами запитів і відповідей; перехід v1 → v2 є breaking change. Ізоляцію орендарів відображено у структурі шляхів `/api/v2/organizations/{orgSlug}/...`.

**Протоколи передачі даних.** REST/JSON over HTTPS. Автентифікація — OAuth 2.0 Client Credentials, Bearer-токен із часом життя 3600 с, гранулярні scopes формату `flex.<category>.<resource>.<permission>`. Дати передаються у форматі ISO 8601 UTC.

**Стек даних і консистентність.** Тип СУБД не розкривається. Фільтрація дозволена лише за індексованими полями; пагінація курсорна, розмір сторінки — до 50 записів.

**Technical Bottlenecks:**

- rate limiting на інтеграцію в межах організації: 400 запитів читання/хв (до 20 000/добу) і 100 запитів запису/хв (до 5 000/добу), перевищення повертає HTTP 429;
- обмеження сторінки 50 записами: синхронізація N сутностей потребує щонайменше N/50 послідовних запитів;
- вилучення параметра `$populate` у v2: пов'язані дані отримуються окремими запитами, що породжує патерн N+1 і прискорює вичерпання квоти.

### 1.2.3 Seatsurfing

**Архітектурний патерн.** Модульний моноліт на Go (маршрутизатор gorilla/mux, шари router → service → repository) з розширеннями у вигляді плагінів, підключених через gRPC. Клієнтська частина — Next.js 16 / React 19. Розгортання — Docker Compose (застосунок і PostgreSQL 18).

**Протоколи передачі даних.** REST/JSON між клієнтом і сервером, gRPC для плагінів, CalDAV для синхронізації з календарями. Автентифікація — JWT, OAuth 2.0 для зовнішніх провайдерів ідентичності, WebAuthn, TOTP.

**Стек даних і консистентність.** PostgreSQL; кеш — in-process freecache (10 МБ) або Valkey. Конфлікти бронювання усуваються транзакційними advisory-блокуваннями PostgreSQL (`pg_advisory_xact_lock`) за ключами користувача та локації з подальшою перевіркою перетину напіввідкритих інтервалів `[enter, leave)` у коді застосунку.

**Technical Bottlenecks:**

- блокування встановлюється на рівні локації, тому операції створення бронювань в одній локації серіалізуються; за пікового навантаження виникає lock contention і зростає p95 Latency;
- блокування утримується на окремій транзакції, що займає додаткове з'єднання з пулу БД на час критичної секції;
- відсутнє обмеження цілісності на рівні схеми (`EXCLUDE USING gist`), тому коректність залежить від того, чи кожен шлях запису в коді встановлює блокування;
- rate limiter використовує in-memory store (за замовчуванням 250 запитів/хв), тому ліміти не узгоджуються між репліками під час горизонтального масштабування.

### 1.2.5 Аналітичний висновок

Встановлено, що комерційні аналоги Nexudus та OfficeRnD Flex реалізовано як закриті мультиорендні SaaS-платформи, в яких інтеграційний контракт обмежено синхронним REST API з жорсткими квотами. В OfficeRnD Flex квота становить 100 операцій запису за хвилину на інтеграцію, сторінка обмежена 50 записами, а вилучення механізму `$populate` породжує патерн N+1. У Nexudus відсутність методу PATCH зумовлює оновлення через повну заміну запису, що за відсутності задокументованого оптимістичного блокування створює ризик втрати оновлень. Внутрішня модель даних і механізми контролю конкурентного доступу обох систем непрозорі, тому гарантію відсутності подвійного бронювання неможливо верифікувати інструментально.

Відкритий аналог Seatsurfing усуває конфлікти бронювання за допомогою транзакційних advisory-блокувань PostgreSQL, однак ключем блокування обрано локацію, а не конкретне робоче місце. Таке рішення серіалізує всі операції створення бронювань у межах локації та спричиняє lock contention і зростання p95 Latency у пікові періоди. Цілісність даних не підкріплено обмеженням на рівні схеми, а in-memory rate limiter не узгоджує ліміти між репліками, що обмежує горизонтальне масштабування.

З урахуванням виявлених обмежень у кваліфікаційній роботі обрано модульну шарову архітектуру на FastAPI з дворівневим захистом від подвійного бронювання. Перший рівень — короткочасне блокування конкретного робочого місця в Redis (`SET NX` з TTL), яке не серіалізує запити до інших місць і автоматично знімається в разі відмови процесу. Другий рівень — транзакційний запис у PostgreSQL з обмеженням `EXCLUDE USING gist` над діапазоном `tstzrange`, що гарантує відсутність перетину інтервалів навіть у разі втрати блокування Redis. Архітектурний компроміс (trade-off) полягає в появі додаткової інфраструктурної залежності (Redis) і складніших сценаріях тестування в обмін на дрібнозернисту гранулярність блокувань, гарантію цілісності на рівні СУБД та спільні для всіх реплік ліміти запитів. Формалізація цих рішень у моделях UML, C4 та схемі даних є предметом Розділу 2.
