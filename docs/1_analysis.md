# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ПОСТАНОВКА ЗАДАЧІ ДОСЛІДЖЕННЯ

## 1.1 Актуальність вибраної теми дослідження

Системи бронювання спільних ресурсів (робочих місць, переговорних кімнат) належать до класу інформаційних систем із конкурентним доступом до обмеженого ресурсу, прив'язаного до часового інтервалу. У пікові періоди кілька клієнтів одночасно ініціюють операції над тим самим ресурсом. За реалізації операції бронювання за схемою «перевірити доступність — записати» без синхронізації виникає стан гонитви (race condition), наслідком якого є подвійне бронювання та порушення цілісності даних. Ручний облік і табличні засоби не забезпечують ні атомарності операцій, ні актуальності стану ресурсів у реальному часі.

Ключова інженерна задача полягає у забезпеченні узгодженості стану ресурсів за паралельних запитів без суттєвого зростання затримки (Latency) відповіді API. Поєднання реляційного сховища з транзакційними гарантіями ACID та обмеженнями цілісності на рівні схеми даних (PostgreSQL), розподіленого короткочасного блокування з обмеженим часом життя (Redis) і stateless REST API (FastAPI) дає змогу усунути конфлікти бронювання, зберегти можливість горизонтального масштабування застосунку та автоматично звільняти ресурс у разі відмови процесу, що утримує блокування. Додатковими вимогами є рольове розмежування доступу (JWT, RBAC), автоматизований контроль якості коду в конвеєрі CI/CD та відтворюване контейнеризоване розгортання.

Відповідно до зазначеної проблеми визначено науковий апарат роботи. **Об'єктом дослідження** є процес керування доступністю та конкурентного бронювання спільних робочих ресурсів коворкінгу в клієнт-серверному вебсередовищі. **Предметом дослідження** є методи та засоби забезпечення узгодженості стану ресурсів під час конкурентного бронювання: розподілене блокування з обмеженим часом життя на основі Redis, транзакційна модель та обмеження цілісності PostgreSQL, шарова архітектура REST API на FastAPI з патернами Repository та Dependency Injection, рольова модель доступу на основі JWT, контейнеризація та конвеєр CI/CD. **Метою роботи** є проєктування та розробка вебсистеми бронювання робочих місць коворкінгу на основі FastAPI, PostgreSQL і Redis із механізмом розподіленого блокування ресурсів для усунення конфліктів подвійного бронювання та забезпечення узгодженості даних за конкурентного доступу.

Оскільки центральною проблемою предметної області є конкурентний доступ до ресурсу з часовою семантикою, вибір архітектурних рішень потребує попереднього огляду відомих підходів до синхронізації, наведеного в підрозділі 1.2.

## 1.2 Огляд сучасних підходів до вирішення відповідних завдань в межах обраного дослідження

Задача запобігання подвійному бронюванню зводиться до забезпечення інваріанта: для кожного ресурсу множина підтверджених бронювань не містить інтервалів, що перетинаються. В інженерній практиці для підтримання такого інваріанта застосовують механізми керування конкурентним доступом (concurrency control) на рівні СУБД, на рівні застосунку та на рівні архітектури взаємодії компонентів.

### 1.2.1 Песимістичне блокування на рівні рядків

Песимістичне блокування реалізується конструкцією `SELECT … FOR UPDATE`, яка утримує блокування рядка до завершення транзакції. Механізм ефективний для оновлення існуючих записів, однак для вставки нового інтервалу відсутній рядок, який можна заблокувати заздалегідь (проблема фантомних записів). Тому на практиці блокують батьківський рядок ресурсу або матеріалізують часові слоти, що збільшує час утримання з'єднання з БД і знижує пропускну здатність під навантаженням.

### 1.2.2 Оптимістичне керування конкурентним доступом

Оптимістичний підхід передбачає перевірку версії запису (поле `version` або ETag) під час оновлення: зміна застосовується лише тоді, коли версія не змінилася після читання. Підхід не утримує блокувань і забезпечує низьку затримку за рідких конфліктів, тому придатний для адміністрування каталогу ресурсів. Для вставки нових бронювань оптимістичне керування саме по собі не застосовне, оскільки конфліктуючі записи ще не існують на момент читання.

### 1.2.3 Рівень ізоляції SERIALIZABLE

У PostgreSQL рівень ізоляції SERIALIZABLE реалізовано через Serializable Snapshot Isolation, що гарантує еквівалентність паралельного виконання деякому послідовному. Ціною гарантії є відкат транзакцій з помилкою серіалізації (SQLSTATE 40001), що вимагає логіки повторних спроб на рівні застосунку; за високої частки конфліктних запитів кількість відкатів і затримка зростають.

### 1.2.4 Обмеження виключення над діапазонними типами

PostgreSQL підтримує діапазонні типи (`tstzrange`) та обмеження виключення `EXCLUDE USING gist`, яке забороняє існування двох рядків, для яких задані оператори повертають істину. Обмеження `EXCLUDE USING gist (workspace_id WITH =, period WITH &&)` (із розширенням btree_gist) декларативно гарантує відсутність перетину інтервалів для одного ресурсу незалежно від коду застосунку; порушення повертає помилку SQLSTATE 23P01, яка транслюється у відповідь HTTP 409 Conflict. Механізм не захищає від повторного надсилання того самого запиту і не надає користувачеві часу на підтвердження вибору.

### 1.2.5 Прикладні (advisory) блокування PostgreSQL

Advisory-блокування (`pg_advisory_xact_lock`) дають змогу серіалізувати критичні секції за довільним ключем у межах однієї БД. Ефективність механізму визначається гранулярністю ключа: блокування на рівні групи ресурсів (локації) серіалізує незалежні запити, як встановлено під час аналізу Seatsurfing у підрозділі 1.3.

### 1.2.6 Розподілене блокування в Redis

Короткочасне блокування в Redis реалізується атомарною командою `SET key value NX PX ttl`: ключ встановлюється лише за його відсутності та автоматично видаляється після закінчення TTL. Механізм забезпечує мікросекундну латентність на стороні сервера та автоматичне звільнення ресурсу в разі відмови клієнта. Водночас блокування з TTL без fencing token не є строгою гарантією коректності: пауза процесу, довша за TTL (збирання сміття, мережеві затримки), дозволяє двом клієнтам вважати себе власниками блокування. Тому в інженерній практиці таке блокування використовують як механізм зниження конкуренції (efficiency lock), а коректність забезпечують на рівні сховища даних.

### 1.2.7 Серіалізація через брокер повідомлень та ідемпотентність

Альтернативою блокуванням є серіалізація запитів через брокер повідомлень (наприклад, розподіл подій за ключем ресурсу між партиціями Apache Kafka). Підхід гарантує порядок обробки в межах ресурсу, однак перетворює синхронну операцію бронювання на асинхронну та потребує додаткової інфраструктури, що надлишково для масштабу одного коворкінгу. Незалежно від обраного механізму синхронізації, повторне надсилання запиту клієнтом у разі тайм-ауту усувається ключем ідемпотентності (заголовок `Idempotency-Key`), за яким сервер повертає результат першої обробки.

Таблиця 1.1 — Порівняння підходів до керування конкурентним доступом

| Підхід | Гарантія коректності | Вартість / обмеження | Застосування у проєкті |
| --- | --- | --- | --- |
| SELECT … FOR UPDATE | Так, для існуючих рядків | Утримання з'єднання, фантомні вставки | Не використовується як основний |
| Оптимістичне (version) | Так, для оновлень | Не застосовне до вставок | Адміністрування каталогу |
| SERIALIZABLE (SSI) | Так | Відкати 40001, повтори, зростання Latency | Не використовується |
| EXCLUDE USING gist | Так, декларативно в СУБД | Потребує btree_gist; немає етапу підтвердження | Основна гарантія цілісності |
| Advisory lock | Так, у межах БД | Залежить від гранулярності ключа | Не використовується |
| Redis SET NX PX | Ні (efficiency lock) | Додаткова залежність | Тимчасове блокування місця (hold) |
| Брокер повідомлень | Так, порядок у партиції | Асинхронність, інфраструктура | Надлишково для домену |
| Idempotency-Key | Захист від дублікатів | Зберігання ключів | Створення бронювання |

Огляд показує, що жоден окремий механізм не забезпечує одночасно строгу гарантію відсутності перетинів, низьку затримку та часове вікно для підтвердження вибору користувачем. Це обґрунтовує комбінований підхід, придатність якого необхідно перевірити на тлі рішень, уже представлених на ринку (підрозділ 1.3).

## 1.3 Аналіз та порівняння існуючих рішень на ринку готових програмних продуктів

Для аналізу обрано три програмні системи, що розв'язують задачу керування робочими місцями та їх бронювання: комерційні SaaS-платформи Nexudus і OfficeRnD Flex та open-source систему Seatsurfing. Аналоги розглянуто як інженерні системи за чотирма аспектами: архітектурний патерн, протоколи передачі даних, стек даних і механізми консистентності, технічні обмеження (Technical Bottlenecks). Характеристики комерційних систем встановлено за офіційною документацією API, характеристики Seatsurfing — за вихідним кодом репозиторію (commit 190ad07 від 27.10.2026). Характеристики, які вендор публічно не розкриває, позначено відповідно і в порівнянні не використовуються.

### 1.3.1 Nexudus

**Архітектурний патерн.** Закрита мультиорендна (multi-tenant) SaaS-платформа. Внутрішня декомпозиція системи публічно не розкривається. Зовнішній контракт — централізований REST API та окремий Public API для клієнтських застосунків. Горизонтальне масштабування контролюється вендором.

**Протоколи та дані.** REST over HTTPS із форматом JSON; методи GET, POST, PUT, DELETE; приймаються з'єднання TLS 1.2 і вище. Автентифікація — Bearer token або HTTP Basic Auth; для інтеграцій передбачено webhooks. Тип СУБД не розкривається; доменна модель реляційна (опубліковано ERD сутностей Coworker, Booking, Checkin).

**Technical Bottlenecks.** Метод PATCH не підтримується, тому оновлення виконується через повну заміну запису за схемою read-modify-write; за паралельного редагування без оптимістичного блокування виникає ризик втрати оновлення (lost update). Підтримка HTTP Basic Auth передбачає передавання облікових даних у кожному запиті. Схема даних, розгортання та інфраструктурний SLA перебувають поза контролем інтегратора (vendor lock-in).

### 1.3.2 OfficeRnD Flex

**Архітектурний патерн.** Мультиорендна SaaS-платформа. API v2 побудовано на NestJS (Node.js, TypeScript) із DTO-схемами; перехід v1 → v2 є breaking change. Ізоляцію орендарів відображено у структурі шляхів `/api/v2/organizations/{orgSlug}/…`.

**Протоколи та дані.** REST/JSON over HTTPS; автентифікація OAuth 2.0 Client Credentials з Bearer-токеном на 3600 с і гранулярними scopes; дати у форматі ISO 8601 UTC. Тип СУБД не розкривається; фільтрація дозволена лише за індексованими полями, пагінація курсорна з розміром сторінки до 50 записів.

**Technical Bottlenecks.** Rate limiting на інтеграцію в межах організації становить 400 запитів читання/хв (до 20 000/добу) і 100 запитів запису/хв (до 5 000/добу), перевищення повертає HTTP 429. Синхронізація N сутностей потребує щонайменше N/50 послідовних запитів. Вилучення параметра $populate у v2 змушує отримувати пов'язані дані окремими запитами, що породжує патерн N+1 і прискорює вичерпання квоти.

### 1.3.3 Seatsurfing

**Архітектурний патерн.** Модульний моноліт на Go (маршрутизатор gorilla/mux, шари router → service → repository) з плагінами, підключеними через gRPC. Клієнтська частина — Next.js / React. Розгортання — Docker Compose (застосунок і PostgreSQL).

**Протоколи та дані.** REST/JSON між клієнтом і сервером, gRPC для плагінів, CalDAV для синхронізації з календарями; автентифікація JWT, OAuth 2.0, WebAuthn, TOTP. Сховище — PostgreSQL; кеш — in-process freecache або Valkey. Конфлікти бронювання усуваються транзакційними advisory-блокуваннями PostgreSQL за ключами користувача та локації з подальшою перевіркою перетину інтервалів у коді застосунку.

**Technical Bottlenecks.** Блокування встановлюється на рівні локації, тому операції створення бронювань в одній локації серіалізуються, що за пікового навантаження спричиняє lock contention і зростання p95 Latency. Блокування утримується на окремій транзакції та займає додаткове з'єднання з пулу БД. Обмеження цілісності на рівні схеми відсутнє, тому коректність залежить від того, чи кожен шлях запису встановлює блокування. Rate limiter використовує in-memory store (250 запитів/хв за замовчуванням), тому ліміти не узгоджуються між репліками.

Таблиця 1.2 — Порівняльна інженерна матриця аналогів

| Критерій | Nexudus | OfficeRnD Flex | Seatsurfing | Проєкт |
| --- | --- | --- | --- | --- |
| Архітектура та розгортання | Закрита multi-tenant SaaS | Закрита multi-tenant SaaS; API v2 на NestJS | Модульний моноліт на Go, плагіни gRPC; Docker Compose | Модульний моноліт (FastAPI, Layered), stateless API; Docker Compose, GitHub Actions |
| API та протоколи | REST/JSON, TLS ≥ 1.2, без PATCH; webhooks | REST/JSON; курсорна пагінація ≤ 50 | REST/JSON, gRPC, CalDAV | REST/JSON, OpenAPI 3, PATCH |
| Сховище даних | Не розкривається | Не розкривається | PostgreSQL; freecache або Valkey | PostgreSQL (ACID) + Redis |
| Захист від подвійного бронювання | Не задокументовано | Не задокументовано | Advisory lock на рівні користувача й локації + перевірка в коді | Redis hold на рівні місця + EXCLUDE USING gist |
| Масштабованість і ліміти | Контролюється вендором | 400 читань/хв, 100 записів/хв; HTTP 429 | Серіалізація в межах локації; in-memory rate limiter | Горизонтальне масштабування API; спільний rate limit у Redis |
| Безпека (AuthN/AuthZ) | Bearer, Basic Auth, RBAC | OAuth 2.0 Client Credentials, scopes | JWT, OAuth 2.0, WebAuthn, TOTP | JWT (access + refresh), RBAC |

Встановлено, що комерційні аналоги реалізовано як закриті мультиорендні платформи, в яких інтеграційний контракт обмежено синхронним REST API з жорсткими квотами, а механізми контролю конкурентного доступу непрозорі; гарантію відсутності подвійного бронювання в них неможливо верифікувати інструментально. Відкритий аналог Seatsurfing усуває конфлікти бронювання, однак ціною серіалізації всіх операцій у межах локації, без обмеження цілісності на рівні схеми та з неузгодженими між репліками лімітами запитів.

З урахуванням виявлених обмежень у кваліфікаційній роботі обрано модульну шарову архітектуру на FastAPI з дворівневим захистом від подвійного бронювання: короткочасне блокування конкретного робочого місця в Redis, яке не серіалізує запити до інших місць і автоматично знімається в разі відмови процесу, та транзакційний запис у PostgreSQL з обмеженням `EXCLUDE USING gist`, що гарантує відсутність перетину інтервалів навіть у разі втрати блокування Redis. Архітектурний компроміс (trade-off) полягає в появі додаткової інфраструктурної залежності та складніших сценаріях тестування в обмін на дрібнозернисту гранулярність блокувань, гарантію цілісності на рівні СУБД і спільні для всіх реплік ліміти запитів. Для конкретизації цих рішень необхідно описати процеси предметної області, в яких виникають зазначені проблеми (підрозділ 1.4).

## 1.4 Аналіз обраної предметної області в межах дослідження (модель As-Is)

### 1.4.1 Загальна характеристика домену

Предметною областю є керування гнучкими робочими просторами (flexible workspace management): коворкінгами та офісами з незакріпленими робочими місцями (hot desking, desk hoteling). Ресурсом домену є пара «робоче місце — часовий інтервал»: одне фізичне місце послідовно використовується різними користувачами в неперетинних інтервалах. З інженерної точки зору домен належить до класу задач резервування обмежених ресурсів із часовою семантикою, спорідненого з бронюванням переговорних кімнат, паркувальних місць і готельних номерів.

Сучасний стан домену визначають такі тенденції: гібридна модель зайнятості, за якої кількість місць менша за кількість користувачів і доступ розподіляється динамічно; перехід до API-first SaaS-платформ з інтеграцією через REST API та webhooks; синхронізація з календарними системами (CalDAV, Microsoft 365, Google Workspace); єдиний вхід через OAuth 2.0 / OpenID Connect; збір даних про фактичну зайнятість для аналітики використання простору. Спільним наслідком цих тенденцій є зростання кількості паралельних джерел запитів до однієї множини ресурсів, що підвищує вимоги до консистентності стану.

### 1.4.2 Актори та сутності

Виділено такі актори: гість (неавтентифікований користувач, якому доступні лише реєстрація та автентифікація); користувач-резидент, який переглядає доступність, створює та скасовує власні бронювання; адміністратор коворкінгу, який керує каталогом зон і місць та будь-якими бронюваннями; системний актор (планувальник), що змінює статус бронювань за часом. Базові інформаційні сутності наведено в таблиці 1.3.

Таблиця 1.3 — Сутності предметної області

| Сутність | Ключові атрибути | Примітка |
| --- | --- | --- |
| User | id, email, password_hash, full_name, role | Роль: user або admin |
| Zone | id, name, description | Логічна зона коворкінгу |
| Workspace | id, zone_id, code, type, equipment, is_active, version | Тип: desk або meeting_room |

### 1.4.3 Процеси та вузькі місця (As-Is)

**Процес 1. Перевірка доступності та створення бронювання.** Доступність місць фіксується вручну (спільна таблиця, месенджер, адміністратор на рецепції) або в програмних системах за схемою check-then-write: клієнт читає список вільних місць, користувач обирає місце, клієнт надсилає запит на створення, сервер повторно читає зайнятість і записує бронювання. Між кроками перевірки та запису існує вікно часу (TOCTOU), у яке паралельний запит може записати перетинне бронювання. За відсутності обмеження цілісності на рівні СУБД коректність залежить лише від коду застосунку; синхронізація через грубозернисте блокування серіалізує незалежні запити, а повторне надсилання запиту після тайм-ауту мережі створює дублікати.

**Процес 2. Скасування бронювання та звільнення ресурсу.** Тимчасове резервування місця на час підтвердження не має автоматичного закінчення терміну, тому покинуті резервування утримують ресурс до ручного втручання. Відсутність перевірки власника дозволяє скасувати чуже бронювання за ідентифікатором (Broken Object Level Authorization, OWASP API1:2023), а фізичне видалення записів замість зміни статусу знищує історію та унеможливлює аудит.

**Процес 3. Адміністрування каталогу місць.** Виведення місця з експлуатації без перевірки майбутніх бронювань створює бронювання на недоступний ресурс. Оновлення через повну заміну запису без версії за паралельного редагування призводить до втрати змін, а кешовані дані про доступність без інвалідації показують застарілий стан.

## 1.5 Постановка задачі та формування вимог

### 1.5.1 Концептуальна модель To-Be

У цільовому стані процес бронювання реалізується як пайплайн із двома рівнями синхронізації:

1. Запит доступності: клієнт надсилає `GET /api/v1/workspaces/availability` з інтервалом і фільтрами; API виконує запит до PostgreSQL з перевіркою перетину діапазонів (оператор &&, GiST-індекс) і виключає місця з активним hold у Redis.
2. Тимчасове блокування: `POST /api/v1/holds` виконує `SET hold:{workspace_id} <token> NX PX 120000`; у разі невдачі повертається 409 Conflict без звернення до PostgreSQL; непідтверджений hold зникає через 120 с.
3. Підтвердження: `POST /api/v1/bookings` з hold-token і заголовком Idempotency-Key; у транзакції виконується вставка, а обмеження `EXCLUDE USING gist (workspace_id WITH =, period WITH &&) WHERE (status = 'confirmed')` відхиляє будь-який перетин; після COMMIT hold знімається.
4. Скасування: `PATCH /api/v1/bookings/{id}` змінює статус на cancelled після перевірки власника; запис зберігається для аудиту, інтервал звільняється.
5. Адміністрування: зміни місць виконуються через PATCH із полем version; деактивація місця з майбутніми бронюваннями повертає 409 зі списком конфліктів; кеш доступності інвалідується після кожної зміни.

Таблиця 1.5 — Відповідність вузьких місць As-Is рішенням To-Be

| Bottleneck As-Is | Рішення To-Be |
| --- | --- |
| Race condition (TOCTOU) між перевіркою та записом | Redis hold (SET NX) + EXCLUDE USING gist у транзакції PostgreSQL |
| Грубозернисте блокування | Ключ блокування — конкретне робоче місце |
| Дублікати після повторних запитів | Заголовок Idempotency-Key |
| Покинуті тимчасові резервування | TTL 120 с, автоматичне звільнення |
| Скасування чужих бронювань (BOLA) | Перевірка власника або ролі admin |
| Втрата історії | Зміна статусу замість видалення |
| Lost update в адмініструванні | PATCH із полем version |

### 1.5.2 Функціональні вимоги (Core Features)

**Модуль Authentication / Users:**

- FR-1. Реєструвати користувача, автентифікувати його та видавати пару JWT (access + refresh) з ротацією refresh-токена.
- FR-2. Перевіряти роль (user, admin) та власника об'єкта для кожного захищеного endpoint (RBAC).

**Модуль Workspaces:**

- FR-3. Створювати, змінювати та деактивувати зони і робочі місця (тип, зона, обладнання, статус) з оптимістичним блокуванням за полем version.
- FR-4. Повертати список вільних місць для заданого інтервалу з фільтрацією за типом, зоною та обладнанням.

**Модуль Bookings:**

- FR-5. Встановлювати тимчасове блокування місця (hold) у Redis з TTL 120 с і автоматичним звільненням.
- FR-6. Створювати бронювання атомарно з перевіркою перетину інтервалів на рівні СУБД, підтримкою Idempotency-Key і відповіддю 409 Conflict у разі конфлікту.
- FR-7. Скасовувати бронювання зміною статусу з перевіркою власника або ролі admin.

**Модуль Cabinet / Administration:**

- FR-8. Повертати історію активних і завершених бронювань користувача з пагінацією; для адміністратора — усі бронювання з фільтрацією за датою, зоною та статусом.

### 1.5.4 Постановка задачі

Таким чином, метою кваліфікаційної роботи є проєктування та розробка клієнт-серверної вебсистеми з модульною шаровою архітектурою на основі FastAPI, PostgreSQL та Redis для вирішення задачі конкурентного бронювання робочих місць коворкінгу без перетину часових інтервалів. Система повинна реалізувати функціональні вимоги FR-1–FR-8, забезпечувати дворівневу синхронізацію (тимчасове блокування місця в Redis і обмеження EXCLUDE USING gist у PostgreSQL) та відповідати нефункціональним вимогам NFR-1–NFR-12, зокрема p95 Latency ≤ 200 мс для читання при 200 RPS і нульовій кількості подвійних бронювань у тесті зі 100 паралельними клієнтами. Розгортання передбачено в контейнерах Docker з автоматизованим контролем якості в GitHub Actions.

## Висновки до розділу 1

У розділі проаналізовано предметну область керування гнучкими робочими просторами, сучасні підходи до керування конкурентним доступом і три програмні аналоги. Встановлено, що комерційні платформи Nexudus і OfficeRnD Flex обмежують інтеграцію синхронним REST API з квотами (до 100 операцій запису за хвилину) та не розкривають механізмів запобігання подвійному бронюванню, а відкрита система Seatsurfing забезпечує коректність ціною серіалізації всіх операцій у межах локації та без обмеження цілісності на рівні схеми. Огляд підходів показав, що песимістичні блокування й рівень ізоляції SERIALIZABLE збільшують затримку та частку відкатів, а розподілене блокування Redis без fencing token не є строгою гарантією коректності.

Обґрунтовано вибір модульної шарової архітектури на FastAPI з дворівневою синхронізацією: короткочасне блокування конкретного робочого місця в Redis зменшує конкуренцію та надає користувачеві вікно підтвердження, а обмеження EXCLUDE USING gist над діапазоном tstzrange у PostgreSQL гарантує відсутність перетину інтервалів незалежно від стану Redis. Таке рішення усуває виявлені в моделі As-Is вузькі місця: стан гонитви між перевіркою та записом, покинуті резервування, дублікати після повторних запитів, несанкціоноване скасування чужих бронювань і втрату оновлень в адмініструванні.

Сформульовано вісім функціональних вимог, згрупованих за модулями Authentication, Workspaces, Bookings та Cabinet / Administration, і дванадцять вимірюваних нефункціональних вимог, зокрема p95 Latency ≤ 200 мс для читання при 200 RPS, нульову кількість подвійних бронювань у навантажувальному тесті зі 100 паралельними клієнтами та покриття коду тестами не менше 70 %. Ці метрики є критеріями приймання програмної системи.

Архітектурне проєктування системи — модель C4, UML-діаграми прецедентів, послідовності створення бронювання та станів сутності Booking, логічна схема даних з обмеженням виключення та записи ADR — є предметом Розділу 2. Безпосередня реалізація вимог, інструментальна перевірка нефункціональних метрик засобами Pytest і k6 та контейнеризоване розгортання розглядаються в Розділі 3.
